# 2026-10-26｜Safari 细化折叠屏适配，OpenAI 强化训练环境隔离

今天的共同线索是：新设备、新自动化和更强模型，都需要更明确的工程边界。Safari 给出折叠屏的渐进增强路径，GitHub 扩大企业应用权限覆盖并披露账号恢复处理，OpenAI 则把训练隔离与存储架构作为基础能力公开讨论。

## 今日概览

### 前端

**折叠屏适配先依赖弹性布局，实验接口与预览版修复则应进入单独的验证清单。**

#### 1. Safari 27.1 给出折叠屏布局与设备姿态的接入边界

**发布日期：2026-10-23。** WebKit 说明，Safari 27.1 在 iPhone Duo 上继续使用相同的 WebKit 引擎；部分折叠状态下，浏览器会把网页中的 PDF 自动切换为双页展示。面向网站开发者的 Device Posture API 与 Viewport Segments API 则仍是功能开关后的开发者预览，并非默认开放的平台承诺。[来源](https://webkit.org/blog/18486/webkit-features-for-safari-27-1/)

两类接口解决不同问题：`device-posture` 媒体查询与 `navigator.devicePosture` 区分部分折叠和连续屏幕状态；视口分段接口描述折叠两侧的可用区域，提供媒体查询、CSS 环境变量与 `window.viewport.segments`。其中 `continuous` 既可能是完全展开，也可能是完全闭合，不能直接当作“使用内屏”的判断依据。

官方建议继续使用 Grid、Flexbox、媒体查询和特性检测，不要通过 UA 识别设备。对现有项目，先检查窄视口、横竖屏和双窗口布局，再在支持接口的环境中追加分段体验；测试可使用 Xcode 27.1 或更高版本中的 Device Hub 模拟器。这样可以把“现有页面正常使用”与“折叠姿态专属体验”拆开验收。

#### 2. Safari Technology Preview 255：优先回归资源加载、文件上传与调试行为

**发布日期：2026-10-22，最近 7 天补充。** STP 255 修复了失败的 `modulepreload` 资源加载停留在缓存中的问题，改为重试；同时修复页面受 service worker 控制时，`fetch` 和 `XMLHttpRequest` 上传磁盘文件可能发送空请求体的回归。[来源](https://webkit.org/blog/18482/release-notes-for-safari-technology-preview-255/)

开发工具方面，Web Inspector 新增 CSS 关键帧动画编辑器、堆栈浮层、控制台求值预览和基础 WGSL 语法高亮。组件侧还修复了 `adoptedStyleSheets` 缩短后仍应用已移除样式表，以及容器尺寸查询把小数尺寸截断为整数等行为。

这些变化更适合作为回归测试入口，而不是一串可直接用于生产的“新特性”。尤其是离线上传、失败后重试、Shadow DOM 样式和临界宽度布局，可针对已有缺陷补充最小复现；官方同时列出无 `body` 文档中 `document.activeElement` 的已知问题，会影响 WebDriver 的 Get Active Element 命令，自动化升级时也应保留兼容性检查。

### DevOps

**企业自动化的重点不只是扩大 API 范围，还要保证权限最小化与身份历史可追溯。**

#### 3. GitHub Apps 企业级安装正式可用，更多管理自动化可摆脱 classic PAT

**发布日期：2026-10-23。** GitHub 宣布企业级 GitHub Apps 安装正式可用，扩展治理、安全与管理权限覆盖。可处理的场景包括企业仓库策略与 rulesets、双因素认证要求、域名验证、IP allowlist、企业访问限制及企业资料等；绕过请求的新增权限是读取权限，不应理解成自动批准。[来源](https://github.blog/changelog/2026-10-23-enterprise-installations-for-github-apps-generally-available)

组织级域名验证和 IP allowlist 的部分覆盖缺口也得到补齐。官方说明，这些更新将进入 GHES 3.24；不能把云端正式可用直接等同于所有现有 GHES 安装已经具备相同能力。

平台团队可以先盘点仍依赖 classic PAT 的企业管理脚本，再按具体工作流配置 App 权限并逐项迁移。价值在于减少对个人凭据的依赖，但“支持更多 API”不等于应为每个应用一次性授予全部管理权限。

#### 4. GitHub 披露 EMU 错删修复：用历史审计事件识别影响范围

**公告日期：2026-10-23；事故发生于 6 月，不是本周新事故。** GitHub 说明，6 月 1—13 日期间，部分经 SCIM 取消配置的 Enterprise Managed User 账号被错误删除，而非进入预期的暂停与混淆状态，影响约 12,285 个账号，其中 76 个在删除时仍处于活跃状态。[来源](https://github.blog/changelog/2026-10-23-emu-deletions-fix)

错误源于新的取消配置处理路径没有正确识别 EMU 账号类型；GitHub 已于 6 月 13 日停用问题路径，并在 10 月恢复受影响的用户记录，使其回到预期的暂停与混淆状态，保留企业内的追溯和审计历史。企业所有者无需执行恢复操作。

管理员可在对应的 6 月时间窗口检查 EMU 账号的 `user.delete` 事件，判断是否受影响。需要明确的是，记录恢复不等于重新激活账号；已完成 hard-deprovision 的 EMU 账号按设计仍不能重新配置。对身份流水线，删除、暂停、混淆和恢复应分别建模，避免把审计可追溯性与访问权恢复混为一谈。

### AI

**模型能力之外，训练隔离与可持续的数据底座正成为 AI 工程公开讨论的重要部分。**

#### 5. OpenAI 强化前沿训练环境隔离，明确当前采用无互联网访问策略

**发布日期：2026-10-23。** OpenAI 发布训练环境安全说明。目标官方页面的搜索摘要显示，公司已强化内部前沿模型训练与评估的隔离措施，并使用其最强模型对边界进行红队测试；基于当前对齐研究、监控系统与互联网基础设施安全状况，现阶段前沿训练采用不访问互联网的策略，直到防护进步足以支持更广泛访问。[来源](https://openai.com/index/securing-our-frontier-model-training-environment)

同一官方摘要说明，在完成修复并改进监控和停止系统后，相关前沿强化学习训练与内部推理于 10 月 1 日恢复，暂停持续 11 天。这是本次公告回顾的处置时间线，不是 10 月 23 日才开始停训。

对自建训练或评估环境的团队，可借鉴的是把网络出口、运行边界、监控和停止能力作为独立控制项验证，而不是只依靠模型遵循指令。本条限于已交叉核对的官方搜索摘要，不推导具体漏洞数量、完整网络架构或“隔离已消除全部风险”的结论。

#### 6. OpenAI 公开 Habitat 存储扩展第二篇：多租户是架构取舍，不是单向升级

**发布日期：2026-10-23。** OpenAI 发布在线存储扩展系列第二篇。目标官方页面的搜索摘要显示，Habitat 已从客户端库与数据库演化为全球分布式存储平台，服务超过 500 PB 数据；本篇集中讨论底层 Azure Cosmos DB 的扩展，以及与 Azure 团队协作形成的共同管理容器方案。[来源](https://openai.com/index/scaling-storage-one-billion-users-part-two)

官方摘要特别描述了多租户路径的往返：从一个多租户 Cosmos DB 容器，转向单租户后端容器，再回到默认采用多租户容器。不能把这个过程简化为“任何业务都应该共享同一个数据库”，更不能把平台存储规模直接当作模型能力指标。

它对 AI 应用工程的启发是：租户布局应结合真实负载、运维方式与全球访问需求重新评估，而不是随业务增长机械增加独立实例。本文只采用目标官方页面摘要中可核实的架构与规模信息，不扩写未核对的延迟、成本或吞吐提升倍数。

## 今日观察

三类更新对应三张不同的检查表：前端检查能力是否默认启用、失败路径能否回归；企业平台检查自动化凭据的权限范围与身份状态；AI 工程检查训练环境能否隔离和停止，以及数据层是否适合当前负载。共同点不是“默认自动化更多”，而是把不同状态、权限和发布阶段区分清楚，再决定哪些能力可以进入生产。
