# Go sync 包与竞态检测：安全汇总学员分数

上一课用 channel 传递学员摘要，并通过取消信号让任务退出。今天换一个问题：多个 goroutine 都要向同一个汇总器累加学员分数，怎样避免同时读写共享数据？

前置课程是[第 14 课：channel 与 select](/docs/golang/daily-golang/lesson-14)。继续使用小李 63 分、小王 80 分、小陈 95 分的样例，只讨论 `sync.Mutex`、`sync.WaitGroup` 与 `-race`；不展开其他锁、原子操作或工作池。

## 学习目标

- 识别多个 goroutine 访问同一变量、且至少一个访问是写入的数据竞争风险。
- 用 Mutex 保护完整的读改写过程，并让所有访问遵守同一把锁。
- 分清 WaitGroup 的“等待完成”和 Mutex 的“互斥访问”。
- 运行竞态检测器，阅读报告中的读写位置，并理解检测的局限。

## 核心概念

### 1. 看起来一行的累加，不等于不可分割

`total += score` 包含读取旧值、计算新值、写回结果。两个任务可能都读到同一个旧值，随后分别写回，其中一次累加就被覆盖了。

数据竞争的重点不是“输出是否刚好正确”，而是不同 goroutine 对同一内存位置的访问缺少同步关系，且至少有一个是写入。即使某次恰好得到正确总分，也不证明程序安全。单核运行同样不能代替同步：goroutine 仍可能交错执行。

### 2. Mutex 让临界区一次只允许一个持锁者进入

`var mu sync.Mutex` 的零值可以直接使用。`mu.Lock()` 获得锁，若锁被占用就等待；`mu.Unlock()` 释放锁。被保护的操作区域叫作临界区。

锁必须覆盖**整个读改写过程**，不能只锁最后的赋值。所有并发读写同一份状态的代码，都必须遵守同一套同步约定；只给写操作加锁、让另一条路径直接读取，仍可能发生竞争。

本课将锁与总分封装在同一个结构体中，用方法统一访问。方法使用指针接收者，避免复制汇总器。Mutex 与 WaitGroup 首次使用后都不能复制；不要按值传递含有已使用锁的结构体。

`defer mu.Unlock()` 能保证方法正常返回或 panic 展开栈时释放锁。锁应尽量只覆盖必要的短操作，不要在持锁时等待其他任务完成。Mutex 不是可重入锁，同一 goroutine 再次锁住自己尚未释放的锁会阻塞。

### 3. WaitGroup 不是共享变量的保护罩

第 13 课已经借用过 WaitGroup，本课把它与锁放在一起区分：

| 工具 | 回答的问题 | 不负责什么 |
| --- | --- | --- |
| Mutex | 谁现在可以访问共享状态？ | 不自动等待所有任务结束 |
| WaitGroup | 登记的任务是否全部完成？ | 不阻止任务之间同时修改变量 |

本课使用兼容前课的 `Add` / `Done` / `Wait` 写法：在启动 goroutine **之前** `Add(1)`，任务内 `defer Done()`，主流程最后 `Wait()`。不能让计数变成负数，也不要在开始等待后才让尚未登记的任务自行增加计数。

`Wait()` 返回后，本例全部累加已经完成，因此主流程能读取最终结果；但任务彼此之间的并发累加，仍必须由 Mutex 保护。

### 4. -race 检测实际执行中发生的竞争

`go run -race .` 会为本次运行加入竞态检测；有测试时可用 `go test -race ./...`。报告通常包含 `WARNING: DATA RACE`、冲突访问的源码位置，以及相关 goroutine 的创建位置。

检测器会增加运行时间与内存开销，需要受支持的平台和工具链。通常还需要启用 cgo 并安装 C 编译器；若出现 cgo 或编译器错误，先解决运行环境，不能把“检测器没能启动”当作“没有竞争”。

一次没有报告，只表示这次执行没有检测到竞争，不是对所有路径的数学证明。它也不负责发现所有死锁、错误的业务规则或遗漏任务。

## 代码示例

在新的空目录执行：

```bash
mkdir lesson15
cd lesson15
go mod init example.com/lesson15
```

把下面完整程序保存为 `main.go`：

```go
package main

import (
    "fmt"
    "sync"
)

type Student struct {
    Name  string
    Score int
}

type ScoreBoard struct {
    mu    sync.Mutex
    total int
}

func (b *ScoreBoard) Add(score int) {
    b.mu.Lock()
    defer b.mu.Unlock()
    b.total += score
}

func (b *ScoreBoard) Total() int {
    b.mu.Lock()
    defer b.mu.Unlock()
    return b.total
}

func main() {
    learners := []Student{
        {Name: "小李", Score: 63},
        {Name: "小王", Score: 80},
        {Name: "小陈", Score: 95},
    }
    var board ScoreBoard
    var wg sync.WaitGroup

    for _, learner := range learners {
        wg.Add(1)
        go func(current Student) {
            defer wg.Done()
            board.Add(current.Score)
        }(learner)
    }

    wg.Wait()
    fmt.Printf("已汇总 %d 位学员，总分 %d\n", len(learners), board.Total())
}
```

运行格式化、静态检查、普通执行和竞态检测：

```bash
gofmt -w main.go
go vet ./...
go run .
go run -race .
```

两次运行都应只输出下面的业务结果，竞态检测不应报告竞争：

```text
已汇总 3 位学员，总分 238
```

阅读顺序：

1. 主流程创建一个汇总器；所有任务调用的都是同一个 `board` 的方法。
2. 循环显式传入当前学员值，任务不修改学员切片。
3. `Add` 持锁执行累加，其他任务要等它释放后才能进入同一临界区。
4. 任务返回前报告完成；主流程等全部任务完成后再打印一次结果。
5. `Total` 也遵守同一把锁，便于以后在任务尚未全部结束时安全读取快照；不过锁本身不保证这个快照已经是最终总分。

主流程没有在持锁状态调用 `wg.Wait()`，也没有在每轮启动后立刻等待。本例只有一个共享整数，使用锁是为了学习共享状态的同步；也可以让任务发送分数、由单一接收者累加，但本课不重复上一课的 channel 方案。

### 对照实验：等待完成，仍然可能竞争

仅在本地实验副本中，把 `Add` 方法替换成下面的**错误版本**；其他代码保持不变：

```go
// 错误示范：多个 goroutine 无同步地读写 total。
func (b *ScoreBoard) Add(score int) {
    b.total += score
}
```

再次执行 `go run -race .`。本例触发竞争时，标准错误中会出现 `WARNING: DATA RACE`，报告会指向 `Add` 中的冲突访问，并以非零状态结束。`go run` 默认通常还会显示 `exit status 66`；外层命令的退出码不必与编译后程序的退出码相同。

本实验不依赖总分一定出错：即使结果仍是 238，只要报告竞争就必须修复。若某次没有触发，不能据此接受错误代码，可重复运行或增加任务量。只在 `Total` 里保留锁没有用，因为其他写入路径没有参与同一套保护。

实验结束后，务必恢复 `Add` 的 `Lock` 和 `defer Unlock`，再执行 `go vet ./...` 与 `go run -race .`，确认正常退出且没有竞争报告。

## 练习

1. 添加 `{Name: "小赵", Score: 72}`，预测并验证输出变成“已汇总 4 位学员，总分 310”。不要手工改 WaitGroup 的总数，仍在循环中登记任务。
2. 在副本中运行错误版本，找出报告里的冲突源码行与 goroutine 创建位置。记录是否报告竞争，不要只记录总分；完成后恢复正确版本。
3. 只做代码阅读：如果把 `wg.Add(1)` 移进 goroutine，为什么主流程可能过早结束等待？如果只有 WaitGroup、没有 Mutex，为什么两个任务之间仍然不安全？
4. 只做代码阅读：如果主流程先 `board.mu.Lock()`，再 `wg.Wait()`，最后才解锁，而任务都需要进入 `board.Add()`，会形成什么等待关系？不要把会挂住的版本留在正式程序里。
5. 使用正确版本执行 `GOMAXPROCS=1 go run -race .`，确认仍为总分 238。解释为什么单核是运行条件，不是删除锁的理由。

自查标准：能分别指出共享数据、保护它的锁、任务完成的登记点与等待点；能根据竞态报告定位冲突，而不是用“多跑几次都正确”代替同步设计。

## 小结

WaitGroup 负责等待任务完成，Mutex 负责协调共享状态访问，两者解决不同问题。把完整读改写放进同一把锁保护的临界区，让所有访问路径遵守约定，并避免复制已经使用的同步对象。`-race` 能发现已执行路径中的数据竞争，但不能替代设计与充分测试。下一课再学习用 `context` 传递取消与超时。
