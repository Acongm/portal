# Go goroutine 入门：并发生成学员摘要与安全传参

上一课用表驱动测试检查学员登记规则，执行过程仍然是按顺序调用函数。今天沿用“小李，当前分数 63”的摘要格式，学习如何让多项独立任务有机会交错推进，并让主程序等待它们完成。

前置知识是第 12 课，以及函数、结构体、切片和循环。本课聚焦 `go` 语句、并发与并行的区别、循环变量捕获；不重复登记校验，也不展开 channel、锁或并发测试。为了得到可以可靠退出的完整程序，会先借用 `sync.WaitGroup` 的三个方法，后续课程再系统学习同步工具。

## 学习目标

- 用 `go f(...)` 启动 goroutine，理解启动不等于任务已经完成。
- 区分并发与并行，不把 goroutine 数量当作同时使用的 CPU 核数。
- 用最小的等待机制保证所有任务完成，不靠 `time.Sleep` 猜测耗时。
- 通过显式参数传递当前循环值，识别闭包捕获共享变量的风险。

## 核心概念

### 1. go 语句启动独立的执行流程

普通函数调用会等待函数返回，再继续下一行。`go printSummary(learner)` 则启动新的 goroutine 执行函数，调用方不等待它返回。goroutine 由 Go 运行时调度，并不是“每启动一个就创建一条专属操作系统线程”。

`main()` 本身也运行在一个 goroutine 中。它一旦返回，程序就退出，不会自动等待其他 goroutine。因此，只写启动代码，可能什么都还没打印程序就结束了。

`go` 调用的函数值与实参会先在调用方求值，再由新 goroutine 执行调用。这个规则是本课通过参数传递当前学员值的基础。

### 2. 并发不保证并行，更不保证变快

**并发**是组织任务的方式：多个任务可以交错推进；**并行**是某一时刻确实有多个任务同时执行。只有一个可用 CPU 执行资源时，多个 goroutine 也能交替运行，但不意味着 Go 代码在多个核上同时执行。

`GOMAXPROCS` 影响同时执行 Go 代码的操作系统线程数量上限，不限制 goroutine 总数。本课不调整运行时参数；练习中只临时用环境变量观察单个执行资源下的行为。

这里的摘要计算非常短，并发的调度与等待成本可能超过工作本身。示例用于理解执行模型，不是性能优化方案，更不能从打印顺序推断实际运行用了几个核。

### 3. 等待完成，不靠睡眠碰运气

本课借用标准库 `sync.WaitGroup`，把它理解为“尚未完成的任务计数”：

- 启动前调用 `wg.Add(1)`，登记一个任务。
- 任务内用 `defer wg.Done()`，保证函数返回时报告完成。
- 主流程用 `wg.Wait()`，等计数回到零再向下执行。

`Add(1)` 必须在相应的 `go` 语句前完成。不要移进 goroutine，否则主流程可能在任务还没登记时就结束等待。本例不复制 WaitGroup，所有任务使用同一个 `wg`。

`time.Sleep` 只是让当前 goroutine 暂停一段时间，不能证明别的任务已经完成。机器负载一变，“睡够了”就可能不成立；等待应该表达完成条件。

### 4. 闭包捕获的是变量，不是自动冻结的快照

匿名函数可以使用外层变量，这就是闭包。如果多个任务捕获同一个仍被修改的变量，它们可能读到后来才写入的值；并发读写还可能产生数据竞争。

循环中有一个需要分清的版本边界：对于声明语言版本为 Go 1.22 或更高的包，`for _, learner := range learners` 中的迭代变量每轮是新的变量，直接捕获它不再具有旧版本的同一种循环陷阱。但如果先在循环外声明变量，再用 `for _, learner = range learners` 赋值，仍然是在反复修改同一个变量。普通外层共享变量也不会因升级版本自动变安全。

本课统一写成 `go func(current Student) { ... }(learner)`：每次启动前先把当前值作为实参求值，再传入函数参数。这样既清楚地表达了数据归属，也避免依赖读者的语言版本知识。

本例 `Student` 只有字符串和整数，任务只读取自己的值，不修改共享分数。值传递不是对所有类型的深拷贝：若结构体里放的是指针、切片或 map，复制结构体后仍可能引用同一份底层数据，不能只凭“传了参数”就断言没有共享。

## 代码示例

在新的空目录中执行：

```bash
mkdir lesson13
cd lesson13
go mod init example.com/lesson13
```

保存下面的完整代码为 `main.go`。为了突出并发结构，本课直接准备三位已知有效的学员，不重新实现前两课的登记包与校验测试。

```go
package main

import (
    "fmt"
    "sync"
)

type Student struct {
    Name  string
    Score int
}

func (s Student) Summary() string {
    return fmt.Sprintf("%s，当前分数 %d", s.Name, s.Score)
}

func main() {
    learners := []Student{
        {Name: "小李", Score: 63},
        {Name: "小王", Score: 80},
        {Name: "小陈", Score: 95},
    }

    var wg sync.WaitGroup
    for _, learner := range learners {
        wg.Add(1)
        go func(current Student) {
            defer wg.Done()
            fmt.Println(current.Summary())
        }(learner)
    }

    wg.Wait()
    fmt.Println("全部学员摘要已生成")
}
```

在含 `go.mod` 的目录执行：

```bash
gofmt -w main.go
go vet ./...
go run .
```

输出包含以下四行，**前三行的顺序不作保证**；最后一行一定在三个任务完成之后：

```text
小李，当前分数 63
小王，当前分数 80
小陈，当前分数 95
全部学员摘要已生成
```

上面的文本按输入顺序列出应出现的内容，不表示调度器会按该顺序执行。`go` 语句的启动顺序不等于函数完成顺序；多运行几次即使恰好顺序一样，也不能建立顺序保证。

逐步理解这段代码：

1. 主流程取得一个学员值，先增加待完成计数。
2. 把当前 `learner` 传给匿名函数的 `current` 参数，启动任务。
3. 任务生成并打印摘要，返回前执行 `Done()`。
4. 主流程启动全部任务后，在 `Wait()` 等待；计数回到零，才打印完成提示。

没有把每个任务的 `Wait()` 放进循环，因为那样会启动一个就等一个完成，把这组工作又组织成顺序执行。今天只需要“全部完成”这个条件，不要求三个任务之间按姓名排序；收集结果、通信和有序输出留到后续课程。

## 练习

1. 添加 `{Name: "小赵", Score: 72}`，先预测输出包含哪些行，再执行。确认每位学员恰好出现一次，完成提示仍在最后，等待代码不需要跟着改数字。
2. 多次运行 `go run .`，记录前三行顺序。解释为什么“这次先打印小陈”与“小陈总会先完成”不是一回事。
3. 执行 `GOMAXPROCS=1 go run .`。确认全部任务仍能完成，说明并发不以多核并行为前提；不要根据一次输出推导性能结论。
4. 在本地副本暂时删掉 `wg.Wait()`，多次执行。可能漏掉任务输出，也可能恰好打印齐；两种结果都不能证明删掉等待是安全的。观察后恢复，重新运行并检查完成提示的位置。
5. 只做代码阅读：如果循环外声明一个 `Student` 变量、循环内反复赋值，匿名函数又直接读取它，会有什么共享风险？用“函数参数在启动前求值”和“闭包读取外层变量”的差别解释为什么本课选择显式传参，而不是认为 Go 1.22 已经修复所有捕获问题。

自查标准：能指出任务在哪里启动、在哪里报告完成、主流程在哪里等待；能说明每个任务读取哪份学员值，且不使用睡眠模拟同步。

## 小结

goroutine 用 `go` 语句启动，由运行时调度；并发描述任务如何组织，并行描述是否同时执行。主程序必须显式等待任务完成，本课用 WaitGroup 建立这一条件。循环中通过参数传递当前学员值，避免误把共享外层变量当成独立快照。下一课再用 channel 与 select 学习任务间通信，本课先把启动、数据归属与退出条件讲清楚。
